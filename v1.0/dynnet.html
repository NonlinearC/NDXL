Simulating Networks With Dynamic Topologies

Note
This page assumes familiarity with the basic layout and API usage described in the main Examples page.

The full code for these examples can be found here.

The focal point of NDXL's architecture is its ability to simulate dynamic networks, which we outlined earlier. This is facilitated by storing the state vector, intermediate stages, slope evaluations, noise matrices, and much more information locally for each agent, rather than in contiguous array over the entire network. Unfortunately, this approach makes NDXL slower and more memory intensive than existing software solutions when simulating large static networks; its advantage remains specifically in dynamic networks.

The most important rule to keep in mind when simulating dynamic networks is that of when agents and noise channels in a network can be added, removed, or modified. To that end, we distinguish between calculation (something that evolves an agent's state vector) and modification (something that alters the dynamics, noise, void* params, or callback of an agent).

Agent dynamics (NDXLVertexDynamics; NDXLEdgeDynamics) and noise functions (NDXLVertexNoise; NDXLEdgeNoise) must ONLY be used for calculation

These functions are called multiple times per step, because all integration methods have multiple stages, and steps in an adaptive stepping algorithm may fail, triggering a retry with a smaller step. Furthermore, intermediate stages are evaluated at fractional increments of the time step between the previous and next step, meaning any modifications in these functions would happen at different times, on different scales, multiple times per step. Such modifications could therefore cause, among other issues: unexpected arithmetic errors, numerical instability, and incorrect error calculations.

Your program will not necessarily crash, your simulation will just be very, very wrong!

Agent callbacks (NDXLVertexCallback; NDXLEdgeCallback) can be used for calculation and modification

Callbacks are only evaluated once at the end of a successful time step, so modifications made will take effect on the next step. You could even use the callback of one agent to modify the properties of another agent, or destroy the calling agent (though this should be the last action taken in the callback to avoid dereferencing NULL).

Network callbacks (NDXLNetworkCallback) can be used for calculation and modification

A network callback is like Annie Oakley: anything the agent callback can do, the network callback can do better.

Network callbacks, as we have seen before, are primarily used to capture simulation output over the whole network as once. In the context of dynamic networks, they are also typically used to

  • Update the states of agents based on network wide rules
  • Evaluate agents and add or remove agents based on certain criteria
  • Reconfigure the topology by changing edge properties

Failing Vertices

As an introductory example, let us consider a network with \(10\) homogeneous vertices whose state vectors evolve according to

\[ \frac{dx}{dt} = xt \]

\[ x_0 = 1 \]

Each vertex is then given a unique "upper limit" to their state, uniformly random between \(0.5\) and \(7\).

// ...
int dynamics(NDXLVertex* vert, double* dx, const double* x, double t, void* p)
{
dx[0] = x[0] * t;
return 0;
}
int main(int argc, char** argv)
{
ndxlInit();
NDXLNetwork* nwk = ndxlCreateNetwork(NULL);
// Prepare initial state and space for each vertex's `void* params`
double x0 = 1.0;
double ulim[20];
// Create vertices
for (int i = 0; i < 10; i++)
{
// Define the upper limit
ulim[2 * i] = randdbl(0.5, 7.0);
// Give each vertex an ID for callback output (see below)
ulim[2 * i + 1] = i;
ndxlCreateVertex(nwk, &x0, 1, dynamics, NULL, NULL, 0, NULL, ulim + 2 * i);
}
}

What makes this network dynamic is the upper limit: if the state of a vertex reaches or exceeds this limit, the vertex "fails" and is removed from the network. To do this, we'll define a vertex callback which destroys its called if this condition is met.

// ...
int callback(NDXLVertex* vert, double* x, double t, void* p)
{
// Extract limit and ID from `void* params`
double limit = ((double*)p)[0];
int id = (int)(((double*)p)[1]);
if (x[0] >= limit)
{
printf("Vertex %d destroyed at t = %f\n", id, t);
ndxlDestroyVertex(&vert);
}
// Importantly, we do not operate on `vert` after it has been destroyed
return 0;
}

// ...
int main(int argc, char** argv)
{

ulim[2 * i + 1] = i;

}
}

...or post-creation using ndxlSetVertexCallback().

Before simulating the network, there is one thing we need to decide, namely, time scale. Because callback is evaluated after each successful time step, a vertex could be destroyed much later than it is supposed to be; consider, for example:

  • Vertex \(1\) has state \(3\) at time \(2\) with a limit of \(5\)
  • The next time step size is 1.7, taking us to time \(3.7\)
  • At \(t=3.7\), vertex \(1\) has a state of \(6\), meaning it will be destroyed
  • But \(6\) is so much larger than \(5\) that it should have been destroyed quite some time before \(3.7\)

Ordinarily this is solved with a continuous condition checker e.g., continuous callbacks in Julia's DifferentialEquations.jl, or events in Python's SciPy. However, NDXL does not (yet) have a mechanism for this, so we must instead poll the callback on such a small time scale that the time of each vertex's destruction is sufficiently accurate. We could do this in one of two ways:

  • Use an adaptive method with time stops at regular intervals
  • Use a static method with a very small step size

Efficiency points us to the second option, so we will use ndxlNetworkSimulateRalston() with \(h=10^{-3}\). We will also print the number of vertices in nwk afterwards to verify the agents have all been destroyed.

// ...
int main(int argc, char** argv)
{
ndxlInit();
// ...
ndxlNetworkSimulateRalston(nwk, 2.0, 1e-3, NULL);
printf("After simulation, network has %d vertices left\n", ndxlGetNetworkOrder(nwk));
return 0;
}
